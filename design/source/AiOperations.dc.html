AI operations — runs waiting, run history, memory, and where the code goes

What a team needs before a run can start and what it leaves behind: why a run is waiting, how to find a run you mean, what one run shows, what the project knows, where a team works and how its code leaves. The board only shows it; the lead decides how to work.
A
What this board decides
The rest of the board only draws these.
The questionThe decisionWhy
What is scarce?The usage window of a Claude account, not money. A run that meets a closed window is waiting, not failed: it does not count a try and starts when the window reopens.The plan is a subscription, so a dollar figure says nothing about what you can still run.
What does a team remember between tickets?Two layers in every prompt: instructions you write, and lessons the teams proposed and you kept.The same mistake is not paid for twice. The lead’s report is where a lesson comes from.
Where does a team work?One git worktree per ticket on its own branch, at a path that does not move. The lead and its roles of that ticket share it.A run can be resumed only if the folder is still the same, and two tickets can run at once.
How does finished code leave?Open a pull request, merge on this machine, or leave the branch. The board guesses from the repository; you change it per project or ticket.A merge happens only because a person asked.
How many runs at once?Two per Claude account by default, and as many as you like once you change it.A third run on the same account waits for a free slot.

Runs once when a worktree is made. The board remembers how long it took (1 min 40 s) and says so before it starts.
Ports · 5181–5199, one per worktree
Handed out when the worktree is made and given back when it goes. A clash is a board fault, not the AI’s.
The rules
  • One worktree per ticket, not per team. The lead and its roles on the same ticket use it one after another, which is what makes a review of real files possible.
  • A fixed path, because --resume needs the folder to still be there and still be the same.
  • Never removed while something is uncommitted. The Remove button is not offered; Keep is.
  • Beside the repository, never inside it. A worktree under the checkout shows as untracked files, and a local merge is refused while the main folder is dirty — an inside path would block every merge.
H
Handing over the code
Three ways out, one guessed from the repository and changed per project or per ticket. A merge happens only because you asked for it, and a conflict is never left half-finished.
Open a pull request
Guessed when the repo has a GitHub remote and gh is signed in. Opened as a draft when the ticket reaches Review, marked ready at Done.
Merge on this machine
Guessed when there is no remote. Only ever when you ask — moving to Done, or the Merge button. Never while the main checkout is dirty.
Leave the branch
Guessed when the remote is not GitHub: the branch is pushed and you open whatever your host calls a merge request.

The rule
Why
Who may merge
Only you, by moving the ticket to Done or pressing Merge. No rule, no AI and no schedule ever merges.
A merge is the one step that cannot be undone from inside the board.
When the main checkout is dirty
The merge is refused, with what is uncommitted listed.
Merging into a tree with your own unsaved work in it is how work gets lost.
A conflict
Never left half-done. The merge is rolled back, and you choose who resolves it.
A repository stuck mid-merge is a board fault that costs an hour to understand.
After a merge
The worktree is removed and its port is given back.
Otherwise four finished tickets quietly hold two gigabytes.
