AI operations — when a run breaks, what it spends, and why it did that

Wave 1 of the AI plan (docs/specs/ai-claude-code-plan.md): the part that has to hold before an AI team is worth having. An AI that hangs is diagnosed before anything is restarted; everything an AI cannot finish by itself lands in one queue with a diagnosis and a way out; the quota of each Claude account is visible, including why work is waiting; every run keeps its own transcript so “why did it do that” still has an answer in three months; the project carries instructions and the lessons the AIs wrote themselves; each ticket works in its own git worktree, and finished code leaves by a route you chose.
A. What this board decides
Every row is a decision already taken in the plan document, and the rest of the board only draws these. The grey chip says where it comes from: D1–D25 are the decisions in section 2 of docs/specs/ai-claude-code-plan.md, #1–#32 the numbered needs in its section 5, and the rest name a section of the document.

Where does work an AI cannot finish go?
One queue called Needs you — the same list as the Needs you tab of the notification panel. Resolve it in either place and both close.
Three screens collect it today: AI Team › Now, a stop in Resources, a signed-out account. #20 #31
What happens when a run stops moving?
Diagnose first, act second. A restart is never the first move, and most causes are found by code, with no quota spent.
A dev server in the foreground, a command waiting for a key and a long test look identical from outside. D25
What is scarce?
The usage window of a Claude account, not money. The board shows a window, what is left and when it reopens.
The plan is a subscription, so a dollar figure on the board is an estimate and says nothing about what you can still run. D17
Who keeps the transcript of a run?
The board keeps its own copy when a run ends. It never reads the CLI’s session files to answer a question.
Claude Code deletes its own transcripts on cleanupPeriodDays (30 by default), so history is being lost now. Log 1
How long is it kept?
The summary of a run forever, the full transcript 90 days, a pinned run forever.
The same 90 days as the notification log, so one retention setting covers both. Log 2
What does an AI remember between tickets?
Two layers in the prompt: instructions you write, and lessons the AIs wrote themselves and you can edit. A searchable knowledge base is wave 3.
Lessons are where the quota saving is: the same mistake is not paid for twice. D18
Where does an AI work?
One git worktree per ticket on ai/<KEY>-<slug>, at a fixed path. Every role of that ticket uses it, one after another.
--resume needs the path to stay the same, and one folder for all members makes two runs collide. D4
How does finished code leave?
Open a PR, merge on this machine, or leave the branch alone. The board guesses from the repo and you change it per project.
A merge only ever happens because a person asked, and a conflict is never left half-done. D6 D7
How many AIs run at once?
Two per Claude account by default, and as many as you like once you change it.
Today the limit applies to API keys only, so the CLI has no limit at all. Survey 1
What counts as the board’s own fault?
An MCP tool that does not answer or returns 5xx, a revoked token, a permission that makes a required step impossible, a broken worktree, a port clash.
An AI calling a tool with wrong arguments is the AI’s to fix and is not counted against it. D11
Who is told first?
A judgement call waits for the PM AI, then you. A board fault comes straight to you.
You should not be the first reader of something another AI could settle. D12

C. An AI in trouble: diagnose, then act
Today a run with no time limit can sit forever and nothing notices. The proposal is not a timeout — a timeout would kill long builds — but a ladder: notice by code, diagnose by code, and only then offer an action that fits the cause. Most of it costs no quota at all.
DV
Dev An has produced nothing for 22 minutes
On KAN-218 · step 14 · started 10:06 · the process is alive, CPU 0%
Diagnosed
What the board found. The last step ran npm run dev in the foreground. It printed ready in 412 ms 21 minutes ago and nothing since. No CPU, no new output, no MCP call open.
What that means. A dev server does not end by itself, so the run is waiting for a command that will never return. The work before it is intact.
Already tried. Nothing. This is the first time this run stopped moving.
Stopping the command ends that child process only. The run goes on from step 14 and is told what happened.
What makes this card different
  • It names the cause, not the symptom. “No output for 22 minutes” is the trigger; the card is about the dev server.
  • It says what was already tried, so you are not the second person to try the same thing.
  • Every action is scoped: stop the command, not the run; nudge the AI, not restart it.
  • Waiting is an action too, with a time on it. Choosing it is not the same as ignoring the card.
1 · Notice
By code, on a timer: no new stream event for N minutes while the run is still marked running. Nothing is concluded yet.
2 · Diagnose
By code first: is the process alive, is the CPU busy, what was the last step, is an MCP call open, is RSS climbing. Only if that is inconclusive, Haiku reads the last few steps.
3 · Act
What the diagnosis allows, under the risk tiers: wait, stop one child process, send a message to the running AI, resume with a note, or hand it to you.
4 · Learn
When the cause is one the project will meet again, the AI proposes a lesson for the project memory (section H).

Where the diagnosis comes from
  • The process and its children, and their CPU and RSS: the board already starts the CLI, so it owns the process.
  • The last events of the stream, which the board already stores as steps.
  • Whether an MCP call is open, which the board knows because it answers them.
  • The CLI’s own words when it reports a usage limit, with the reset time.
What the board will not do
  • Restart a run before it has a diagnosis. That is what happens today for memory, twice, and it is the thing this section replaces.
  • Spend quota on a diagnosis it can make by code.
  • Stop a whole run when stopping one child process is enough.
  • Apply Haiku’s reading on its own: an AI’s guess about an AI is still a guess.

What makes a step answerable
  • Every step opens. A command shows what was sent and what came back, with its exit code and how long it took.
  • The first step opens on what the AI was given: the model, the account, the system prompt, the memory, the ticket, the tools, the workspace. That is the “why”.
  • A skill or a subagent is a step of its own, so “was the skill actually used” has an answer. Today the stream is not read for it at all.
  • A failure is a step too, and it carries the same diagnosis the Needs you row carries. One text, two places.
What it costs to keep
  • Compressed, in the board’s own data folder. A busy project is a couple of gigabytes for ninety days, and the screen says how much.
  • Nothing is read from Claude Code’s session files at display time. They are gone after thirty days, and the board must not depend on them.
  • Secrets are masked on the way in, not on the way out.
  • A run can be exported as Markdown or JSON — one run, or everything that happened on one ticket.

Where a lesson comes from
  • When a ticket ends, a light model reads the run and proposes at most one lesson. It costs very little and it only runs once per ticket.
  • A diagnosis in section C can propose one directly: a dev server that hung is exactly the kind of thing worth remembering.
  • You can write one yourself, and you can edit or delete any of them.
  • Nothing is added to the prompt without you keeping it. A proposal sits in this screen until you decide.
How it changes what is written today
  • Today the board writes its block into CLAUDE.md in the working folder, between markers, per member. That stops.
  • It moves into the system prompt of the run (--append-system-prompt-file), which is where it belongs: it is the board’s text, not the repo’s.
  • The repo’s own CLAUDE.md is left alone and still read by the CLI. Two sources, neither overwriting the other.
  • Because the prompt is fixed at the first request of a conversation, changing any of this takes effect on the next run, and the screen says so.

Not a git repository?
The board says so once and falls back to one shared folder, the way it works today. Nothing silently changes behaviour.
The rules
  • One worktree per ticket, not per member. Dev, Reviewer and Tester of the same ticket use it one after another, which is what makes a review of real files possible.
  • A fixed path, because --resume needs the folder to still be there and still be the same.
  • Never removed while something is uncommitted. The Remove button is not offered; Keep is.
  • Roles with no ticket — Board AI, Triage — read the main checkout and do not take a worktree.
What it replaces
  • Today every member of a project shares one working folder, and the board writes skills, hooks and .mcp.json into it.
  • Two runs in that folder edit the same files. Nothing says so, and nothing stops it.
  • A branch is only a label on the ticket: there is no state, no size, and no way to clean one up.
  • Settings › Repositories exists as a row in a table and has never been drawn.

Why these live together
  • Every one of them is a thing a run needs before it starts: a slot, a folder, a port, a prompt, a place for the history.
  • They are per project, because two projects on one machine do not share a repository or a prepare command.
  • Two are not: how many run per Claude account, and the retention, which is the same number as the notification log.
  • The guessed values say they were guessed. Changing one stops it being guessed again.
What it does not do
  • No model or effort per member here — that stays on the member, and per step is wave 2.
  • No dollar budget here. The budget screens stay where they are; this page is about what makes a run possible.

L. The states each of these screens has to have
Not decoration. Four of these are the states the current screens get wrong, and the fifth is the one that only appears on somebody else’s machine.
Needs you is empty
Not a blank panel. “Nothing is waiting on you. 3 AIs are working, 1 is queued.” The count in the sidebar goes away with it.
A run is retrying
An amber line on the run, not an entry in Needs you: “Lost the connection. Trying again in 2 minutes — second of three.” With a Stop trying button.
Nothing can be concluded
The diagnosis line says so instead of guessing: “No output for 22 minutes, and the board cannot tell why.” The four ways out are still there.
The transcript is gone
A run older than the retention keeps its summary and says “the full transcript was removed on 4 Aug”, with a Pin button that is too late and says so.
The repository is not git
One line on Repositories, and the worktree table is replaced by the old shared folder. Said once, not on every run.
The account signed out
One entry for the account, not one per member. Every run on it is held, not failed, and resumes by itself after a sign-in.
The quota is not known
The bar is grey and says not known rather than drawing a number the board invented. The reset time is only shown when the CLI gave one.
History is empty
A new project has no runs. “Nothing has run yet. Runs are kept from the moment the first one ends.”
Everything is paused
Pause all AI already exists. On these screens it means: the queue still fills, the diagnosis still runs, and nothing starts.
M. Where the data comes from, what is decided, and what is still open
The first table is for whoever builds it: what already exists, what is new, and what each thing is for. The two cards below separate what the design has settled from what only the build can answer.
Where it comes from
Notes
A run and its steps
Exists — AiRun: steps, files, report, tokens, cost, state, status changes.
Unchanged. The run detail reads it, and the summary is what is kept forever.
The transcript
New. Written when a run ends: the prompt, every tool call with its arguments and result, what the AI said, the skills used.
Compressed on disk, masked for secrets, searchable (FTS), deleted at the retention unless the run is pinned.
The diagnosis
New, on the run: what the board concluded, what it tried, and when.
One text, shown on the run, in the Needs you row and in the notification. Never written three times.
The Needs you queue
Reuses the notification row. A row with kind = needs_you and a reference to the run.
So that resolving it in either place closes both, which the notification design already decided.
Account usage
New, per Claude account: what the board itself spent in the window, and the reset time the CLI last reported.
An estimate and labelled as one. The reset time is exact, because the CLI gave it.
Project knowledge
New: instructions (one text per project) and lessons (a row each, with the ticket it came from and a use count).
Both go into --append-system-prompt-file. The block the board writes into CLAUDE.md today goes away.
A worktree
New: ticket, path, branch, port, size, state, and whether anything is uncommitted.
Read from git on the machine; the board stores only the mapping.
Hand-over
New, per project: the chosen route and whether it was guessed.
Plus, per ticket, an override.
Decided before building
  • Diagnose before acting. No screen offers a restart as the first move, and no restart happens without a line saying why.
  • One Needs you list, shared with the notification panel. The name is kept, and resolving it anywhere closes it everywhere.
  • Hitting a usage window is not a failure. It does not count a try, does not fail a run, and does not reach Needs you unless the ticket is urgent and no other account has room.
  • The board keeps its own transcript. Nothing on these screens reads Claude Code’s session files, because they are deleted after about 30 days.
  • 90 days for the transcript, the same number as the notification log, set in one place. Summaries and pinned runs are kept forever.
  • One worktree per ticket, shared by the roles of that ticket, never removed while something is uncommitted.
  • A merge is yours. No rule, no schedule and no AI merges, and a conflict is rolled back rather than left half-done.
  • Two runs per Claude account by default.
What the build still has to settle
  • How much of a window is left. The CLI does not publish it. The design draws the board’s own count and says it is an estimate; if the experiment in S5 finds a real source, the bar stops being a guess and the label goes.
  • Sending a message to a running AI. The diagnosis in C offers it, but it needs --input-format stream-json and a change to how the board starts the CLI (S6). Until that works, the action is not shown.
  • How big a transcript really is. 2.1 GB is a guess from the current step volume. If it turns out much larger, the default retention is the thing to revisit, not the feature.
  • Whether a lesson should ever be added without you. The design says no. If six months of keeping almost every proposal says otherwise, it is one switch.
  • Who the coordinator is. The settings page picks a member. Whether the Board AI can be that member belongs to wave 3, where the Board AI changes anyway.
