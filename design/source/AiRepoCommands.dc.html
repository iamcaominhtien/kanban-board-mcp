Screen — v1 proposal

The AI sets up the project’s commands — it reads the repository, tries them, and shows the proof

The middle of the Set up the AI team wizard is redrawn. The old detector guessed the commands and the trial failed with npm: command not found on a machine that has npm, because an app opened from the Dock does not see Homebrew. Now an AI reads the repository and tries each command, and the person sees a result per command: where it came from, whether it works, and the environment it needed. Typing is possible at every point. Based on main at 3.23.0; project names and numbers are illustrative.
A. Why this part of the wizard is redrawn
Only the middle of the wizard changes: What it suggests loses its commands, and Try the commands becomes Commands, where an AI reads the repository, tries each command once in a temporary copy, and shows its evidence. The team, the workflow, hand-over, worktrees, plugins, ports, I will do it myself and Confirm stay as they are on main. Typing the commands by hand stays possible at any moment.
How to read the new step
  • The stepper keeps four steps: Read the repository (code only, no quota), The team (what it suggests, minus the commands), Commands (this board), Confirm.
  • Step 3 has three looks: choose, AI working, result. Typing yourself skips the middle one.
  • Nothing is created until Create, as before. The AI run is the only thing that starts earlier, and it does not edit your checkout.
What does not change
  • Roles and their names, the default workflow, hand over by, a worktree for each ticket, plugins, ports.
  • The footer buttons Back and I will do it myself.
  • Step 4 Confirm, apart from one light warning (frame D5).

Try the commands fails with npm: command not found (exit 127)
The app opened from the Dock gets a minimal PATH, without Homebrew or nvm. The trial runs through /bin/sh with that PATH (repo_scan.py, shell=True).
The AI records the folder that made it work. The result screen shows it as an environment block you can read and edit.
The Test line says “not tried (no command)” when prepare failed
The trial stops at the first failure, so the test is never run, and the screen prints the same words it prints when there is no command (TeamWizard.tsx Trial).
Every command gets its own row and its own status. A command that did not run says why: “prepare failed first”, “no build script found”.
A tools folder lands in prepare
The detector picks whatever looks like an install step, including uv --directory .github/skills/…/scripts sync.
The AI names where each command comes from (CI file, package script) and says which folder is the application. A wrong source is visible, and one click on Ask the AI to fix corrects it.
The same minimal PATH hits every later run
The prepare command of each ticket (worktrees.py), the lint, build and test checks of a workflow (workflow.py) and the AI members’ own runs (cli.child_env(), used by runs.py) all start from the app’s own environment.
A command that passed in the wizard has to pass later. So what is learned is saved with the project as one environment for everything it runs, and applied in all four places.
B. Step 3 · Choose how the commands get set
The AI is the default because it is the way that has proof; typing is one click away and is the default when there is no login to use. The permission note (the AI only reads; the repository’s own scripts run in a temporary copy) sits here, before anyone presses Start, and again as a footer while it runs.

B1
What the code needs (proposed, not built)
The AI run
A server job with progress events, a log, Cancel, and a 10 minute stop. The AI reads the repository from a temporary copy and has no write tools; it proposes as structured output: commands, where each came from, extra PATH folders, notes. It may reuse the CLI search in services/ai/cli.py (the install folders it already knows).
The proof comes from the server
The board runs each proposed command itself, the way a ticket will: subprocess.run(shell=True), the saved environment in front of the PATH, the same shell. The row status comes from that run, never from the AI’s own shell. The AI’s log stays as context. So Run and the status always mean the same thing, and “works in the wizard” cannot mean “fails on the ticket”.
Each command is a result
A trial today runs prepare then test and stops at the first failure (repo_scan.py), leaving trial.test empty. It needs lint and build too, a status per command, and a reason when one did not run.
A failing check costs every ticket
The check step runs lint, build, test in that order, stops at the first failure and sends the ticket back to Dev with “The checks failed” (workflow.py). A command that already fails on the base branch would send every ticket back. So each check command needs a switch, use as a check, that the wizard sets and the check step respects; a command that is saved but off stays out of the loop.
The environment
One extra PATH list stored with the project and put in front of the PATH for the trial (repo_scan.py), the ticket prepare (worktrees.py), the workflow checks (workflow.py) and the AI members’ runs (cli.child_env() in runs.py). Today all four use the app’s own environment.
Two kinds of red
The status needs to tell “the shell could not run it” (exit 126, 127, a missing script) from “it ran and the project failed”. The server decides from the exit code and the output; the AI only adds the explanation.
What stays untouched
Scan, suggestion and Create keep their routes. The team half of the suggestion is the same call without the commands.
