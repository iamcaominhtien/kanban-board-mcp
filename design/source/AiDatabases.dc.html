Screen — v1 proposal

Choose your database — SQLite, PostgreSQL or MySQL/MariaDB, and move between them

App settings › Storage & backup gets a Database card. SQLite stays the default; PostgreSQL and MySQL/MariaDB are real alternatives, with a test that explains what it finds. Moving data is one four-step flow that can be run three ways: a button in Settings, a script, and an AI that helps when a copy stops. Redis and MongoDB are left out on purpose, and the board says why. Based on main at 3.35.1; names, hosts and numbers in the mock-ups are illustrative.
A. What is supported, and how data moves
SQLite stays the default and the only choice that needs no setup. PostgreSQL and MySQL/MariaDB become real alternatives, set in App settings › Storage & backup. Redis and MongoDB are left out on purpose, with the reason on the page. The three migration ways share one flow, so the person learns one thing.
Database
What it is for
Why, and what it costs
SQLite
The default, as today: one file in the data folder, nothing to set up. Still the right choice for one person on one computer.
Nothing changes for anyone who does not open the new card.
PostgreSQL
Version 14 or newer. For a server you already run, backups with your own tools, or a team.
The same models and migrations as SQLite; both go through SQLAlchemy.
MySQL / MariaDB
MySQL 8 or MariaDB 10.6 and newer, with the utf8mb4 character set.
One extra driver, one extra family of checks (character set, user rights).
Redis, MongoDB
Not offered, not even as an export target.
The board is relational: projects, tickets, members, docs and AI runs refer to each other through 87 tables with foreign keys, kept in step by 63 migrations. A key-value or a document store would be a rewrite of the data layer, and it could not keep those guarantees.
Moving between them
Three ways to the same result: a script, a button in Settings, and an AI that helps when a copy stops.
The script and the button run the same copy code. The AI proposes a fix; the board applies it and re-checks the counts. Any direction works: SQLite to Postgres, Postgres to MySQL, back to SQLite.

The script (command name is illustrative)
What it does
--from URL
The database to read. SQLite file, PostgreSQL or MySQL/MariaDB.
--to URL
The database to write. It must be empty, or pass --empty-first (asks you to type its name).
--dry-run
Check both ends and print the plan. Writes nothing.
--verify
After the copy, compare counts, samples, links and counters. Exit 1 if anything differs.
--resume
Continue an interrupted copy from the table it stopped at.
KANBAN_DB_PASSWORD
Read from the environment so the password is not in your shell history.
Exit codes
0 done · 1 verify failed · 2 cannot connect · 3 target not empty · 4 stopped (resume it)

What the AI is shown
The error, the table and column names, the column types on both sides, and row counts. Not the rows themselves and never the password. If it needs an example row it asks, and you choose whether to attach it.
What the AI suggests
Not run yet
Likely cause. The board declares plain text fields without a length. On MySQL and MariaDB the model library turns each of those into VARCHAR(255); SQLite and PostgreSQL do not limit them. An idea page does not fit in 255 characters.
Proposed change, on the new database only:
proposed script
-- 1 column, on the target
ALTER TABLE idea_ticket
MODIFY body LONGTEXT;
-- then: resume from idea_ticket, and re-check
What it affects. This column, and any other text column where a value would not fit: the AI lists them before it runs anything. Your SQLite file is not touched.
The AI proposes; the board applies. It runs the statement, resumes the copy and re-checks the counts itself. The AI’s own words never decide whether the copy succeeded.
This is a gap in the app, not in your data: long text fields should be declared as text once, in the models (section F), so nobody has to widen columns by hand.

Question
Recommendation
Drawn in
May several apps use one PostgreSQL?
Allowed, not promised. The board shows a notice when another app is connected, and live updates between two apps are not guaranteed (see the code table: the change watcher is SQLite-only). Say so on the card.
B1
Where does the password live?
The system keychain on desktop (the app already depends on keyring); the environment variable on a server. The settings file holds engine, host, port, database, user and SSL mode, never the password.
B1, B3
The environment variable or Settings: which wins?
The variable wins and locks the card, as drawn. A person who sets it on a server expects it to hold. This is the reverse of the data folder, where Settings wins over the desktop’s default.
B3
Attachments in a shared database?
Out of scope. They stay in the data folder and the move says so (D0). Putting them in the database or in object storage is a separate design.
D0
Should the AI see rows?
No, unless you attach one. Table and column names, types, counts and the error are enough for nearly every stop, and the password is never sent.
D4
What the code needs (proposed, not built)
One connection setting
database.py builds sqlite+aiosqlite:///{path} and nothing else. It needs a setting (engine, host, port, name, user, SSL) in config.py, the password in keyring, and KANBAN_DATABASE_URL taking precedence. reinit_db already re-points the engine, so a switch needs no restart.
Drivers
An async PostgreSQL driver and an async MySQL driver as extras, bundled by the desktop spec (desktop/common_spec.py) and installed with the server for the web version.
SQLite-only code
init_db sets PRAGMA journal_mode=WAL. events.py watches other processes with PRAGMA data_version (the stdio MCP process writes to the same file). docs_search.py, kb.py and the migrations e6611f7871e7 and c0d1e2f3a4b5 create FTS5 virtual tables, with a fallback already written for builds without FTS5. Each needs a path per database.
Long text
A plain str field is VARCHAR without a limit on SQLite and PostgreSQL, and VARCHAR(255) on MySQL and MariaDB (the model library’s default). Fields that hold pages and comments, such as idea_ticket.body or ticket.description, must be declared as text before MySQL can be offered; otherwise the copy stops as in D4.
Migrations
63 revisions, written for SQLite (render_as_batch=True, PRAGMA database_list in f4a6b8c0d2e4). A new engine could start from the models and be stamped at head instead of replaying all 63, and CI should run them on both servers.
The copy
Reflect both sides, order tables by foreign keys, copy in batches, convert booleans, JSON and datetimes, reset sequences on PostgreSQL, then verify counts, samples, links and counters. One module used by the CLI and by the Settings route, both able to run in either direction.
Export and import
data.py zips kanban.db after a WAL checkpoint and checks it with sqlite3. It needs a dump format that does not depend on the engine, and an import that reads either.
The AI helper
It reads a bundle the server builds (error, names, types, counts), proposes a statement or a script, and the server runs and checks it. It reuses the AI operations on main and has no database credentials.
Tests
CI with PostgreSQL and MySQL service containers, and a round trip: SQLite to Postgres to MySQL to SQLite, compared row by row.
