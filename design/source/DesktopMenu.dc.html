Desktop — menu bar

The menus of the desktop app on macOS and on Windows and Linux. Today Help is empty on macOS and points to the wrong project on Windows. This board designs a real menu: what is in each menu, how it differs by platform, the small windows it opens, and its states. Design only.
A. What is wrong today and what changes
The desktop app has no menu of its own. It shows the default Electron menu, so Help is empty on macOS and points to the wrong project on Windows. A real menu bar is also where people look for shortcuts, settings and ways to get help. This board is only the design of the menus and the small windows they open; it does not change the app.

What is macOS-specific
  • The first menu carries the app name. About, Check for Updates, Settings and Quit live there, so they are not repeated in Help.
  • macOS puts a search box at the top of the Help menu. It finds any menu item by name across all menus, so every item needs a clear name. This is automatic when the menu has the standard Help role.
  • Items that open a window or need more input end with …. Items that act at once do not.
  • Settings uses ⌘, and Hide, Quit and Minimize use the system keys. They are not changed.

What is different on Windows and Linux
  • There is no app menu. Settings is in File (Ctrl+,) and Exit is the last item of File.
  • Check for Updates and About are at the bottom of Help.
  • The menu bar can be hidden and shown with Alt (the default for these platforms); the window title does not change.
  • Shortcuts use Ctrl instead of ⌘. A few differ on purpose (New Idea is Ctrl+Shift+N; Toggle Developer Tools is Ctrl+Shift+I).
  • No search box in the menu. The Keyboard Shortcuts window searches commands as well as keys, so people can find items there.

G. Rules
Proposed.
Naming and order
  • Same words as in the app: “Settings”, “Docs”, “Idea Space”, “Export Logs”.
  • An ellipsis (…) means more input or a window follows. No ellipsis means it acts at once.
  • Order inside a group: most used first. Groups are separated by lines and are not longer than five items where possible.
  • Each item has one place per platform. Nothing is in two menus.
Privacy and safety
  • No menu item sends anything on its own. Report an Issue only opens a page in the browser, after showing what it will fill in.
  • Diagnostics contain versions and system facts only: never tickets, Docs, paths, keys or logs.
  • Developer tools are a normal menu item, not a system-wide shortcut.
  • Links go to this project’s own pages (README, Releases, Issues), never to Electron.
For whoever builds it
  • It is a native menu, so it cannot be styled. Only names, order, shortcuts, enabled state and check marks are designed here.
  • The menu is built per platform in the main process; items that open pages send one message to the app, which uses the same routes as clicking the page.
  • The standard Help role gives macOS its search box. Use standard roles for Edit, Window and Services so the system adds its own items.
  • Disabled state follows backend status and whether a window is open. Check marks follow the current view.
H. What each item opens
Almost every item opens something the app already has. Reuse = already designed, only the menu entry is new. New = a small new window or behaviour (drawn in section E). Native = the system does it (browser, file manager).

I. Check for Updates…: what you see
The update flow is already built in the app: a card in the corner (Download, Later, Skip this version, What’s new) and the Updates section in Settings. The canvas did not show the corner card, so it is drawn here as it is today. The menu item adds only one thing: a toast that answers when the check was started by hand. The automatic checks (at start and every 6 hours) stay silent unless an update exists.
